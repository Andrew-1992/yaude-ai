# Juba Arabic data collection guide

This is the one part of the Sanadi AI dataset that can't be automated,
scraped, or generated by me without real risk of producing wrong or
unnatural Juba Arabic and training the model on it. It needs you — or
someone else fluent in Juba Arabic technical/everyday speech — in the loop
for every example.

## Why this matters more than it might seem

A model that produces confidently wrong Juba Arabic is worse for your users
than a model that admits it can't help in Juba Arabic yet. Bad output in a
language your users trust you to get right will cost credibility fast,
especially with a first cohort of students who are exactly the people who'd
notice.

## How to fill in `template.csv`

Each row is one training example, in both languages side by side so the
model learns the pairing.

| Column | What goes here |
|---|---|
| `id` | Keep as-is or extend the numbering (ja-004, ja-005, ...) |
| `task_type` | One of: `code_generation`, `code_debugging`, `code_explanation`, `research_summary`, `research_writing` |
| `difficulty` | `intro`, `intermediate`, or `advanced` |
| `english_instruction` | The question/task in English |
| `english_response` | The correct answer in English (code blocks fine — use `\n` for line breaks within the cell, or switch to a spreadsheet tool that handles multi-line cells) |
| `juba_arabic_instruction` | The **same** question, in natural Juba Arabic — not a literal word-for-word translation, but how someone would actually ask it |
| `juba_arabic_response` | The answer in Juba Arabic. Technical terms (function names, keywords like "loop" or "variable") can and probably should stay in English if that's how you and other developers actually talk — code-switching is realistic, not a flaw |
| `reviewer_name` | Who verified this row is correct and natural |
| `reviewer_verified` | `TRUE` only once someone has actually read it and confirmed it's right — leave `FALSE` until then |
| `notes` | Anything worth flagging — e.g. "not sure this phrasing is common outside Juba city" |

## Two realistic ways to fill this in

**Option A — you write it directly.** For examples close to your own
technical vocabulary, you can likely write both sides yourself faster than
reviewing someone else's attempt.

**Option B — draft then verify.** Someone drafts a Juba Arabic version
(possibly with AI assistance as a starting point), and a fluent reviewer —
ideally not the same person — checks it before `reviewer_verified` is set
to `TRUE`. Never skip the independent check on this path; a draft nobody
has verified is not data, it's a guess.

**Do not** mark `reviewer_verified` as `TRUE` without an actual review
happening. The eval script (`scripts/evaluate.py`) and the data prep script
both trust this column — if it's wrong, bad data flows straight into
training.

## Once a batch is filled in and verified

Loading verified rows from this CSV into the training set is a small addition
to `scripts/prepare_data.py` (a `load_juba_arabic_examples()` function reading
`data/juba_arabic_intake/template.csv`, filtering to `reviewer_verified == TRUE`,
and yielding `SFTExample` objects with `language=Language.JUBA_ARABIC` or
`Language.MIXED` for code-switched rows). Ask me to wire that in once you have
even 10-15 verified rows — no need to wait for a large batch before we connect
it to the pipeline.

## A realistic target for a first pass

Don't aim for hundreds of rows before this becomes useful. Even 20-30
well-verified examples, spread across task types, is enough to:
- validate that the fine-tuning pipeline handles Arabic-script text
  correctly end to end (tokenization, generation, display)
- give you and any reviewer a feel for how much time each row actually takes,
  so you can estimate what a larger batch would cost
- start surfacing whether Qwen2.5-Coder's base multilingual ability is
  strong enough to build on, or whether the phase 1 model choice needs
  revisiting (see the fallback note in the main README)
